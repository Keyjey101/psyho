# Ника: адаптивная стойка + долгосрочный план работы

## Context

Сейчас PsyHo ведёт диалог по **жёсткой временно́й дуге**: `SessionPhase`
(INTAKE→FOCUS→WORK→INTEGRATION→CLOSE) вычисляется чисто по проценту
`exchange_number / max_exchanges` (`orchestrator.py:_get_phase`). Память —
это **плоский текстовый блок ≤400 слов** (`UserProfile.long_term_memory`),
который пересобирается раз в 3 обмена. Системный промпт уже запрещает
клише и «дружеский» тон, но фаза диктует поведение по таймеру, а не по
ситуации.

Пользователь хочет, чтобы Ника:
1. строила **долгосрочный план работы** и **формулировку случая** (рабочую
   гипотезу о корневых причинах), помнила их между сессиями и шла к
   приоритетам **постепенно**, по одному фокусу;
2. **выбирала способ ответа по контексту**, а не по таймеру: иногда быстрая
   помощь, иногда сбор анамнеза, иногда «просто поговорить» без видимого
   протокола, а иногда — мягкий вызов/сократический вопрос **вместо**
   автоматического отражения эмоций и одобрения (это не всегда полезно);
3. перестраивала приоритеты, если человек говорит «давай не про это сейчас».

### Решения пользователя (зафиксированы)
- **Видимость:** новой страницы НЕТ. Текущий фокус + прогресс показываются
  мягко только в `SessionEndCard`. В самом диалоге Ника протокол не озвучивает.
- **Управление:** пользователь не редактирует план напрямую. Ника
  перестраивает приоритеты по сигналам в чате.
- **Модели (гибрид):** `glm-4-flash` — выбор стойки на каждый ход (низкая
  задержка); `glm-5` — глубокие пересборки плана/формулировки в фоне.

## Архитектура (обзор)

Два новых слоя поверх текущего потока `classify → select agents → synthesize`:

- **Стойка хода (быстрый слой, glm-4-flash):** один вызов на ход, который
  становится главным драйвером *как* отвечать. `SessionPhase` понижается до
  второстепенного «мы близко к концу сессии» сигнала.
- **Клинический слой (медленный, glm-5):** персистентная формулировка случая +
  приоритизированный план фокусов; строится/обновляется в фоне после сессий,
  инжектится в синтез как **внутренний** контекст, мягко отражается в
  `SessionEndCard`.

Обратная совместимость: всё новое инжектится только при непустом
`TreatmentPlan`. Нет плана → поведение ровно как сейчас.

## 1. Модель данных

**Новая таблица `treatment_plans` (1:1 с пользователем), план как JSON в одной
строке** — мы всегда читаем/пишем план целиком, фокусов мало (3–6),
под-запросов по полям нет, нормализация ничего не даёт. JSON-в-TEXT — тот же
паттерн, что `continuation_context` и `agents_used`.

В `backend/app/models/models.py`:
```
class TreatmentPlan(Base):
    __tablename__ = "treatment_plans"
    user_id         String(36) PK, FK users.id ondelete CASCADE
    formulation     Text          # glm-5: запрос, рабочая гипотеза о корнях, ресурсы
    focus_areas     Text          # JSON: [{"id","title","rationale",
                                  #         "status":"active|queued|done","progress":0-100,"order":N}]
    active_focus_id String(36) nullable
    plan_summary    Text nullable # мягкая фраза для SessionEndCard (отдельно от formulation!)
    version         Integer default 1
    plan_hash       String(64) nullable   # SHA1-dedup, как memory_hash
    last_session_id String(36) nullable
    created_at / updated_at DateTime
```
Одна колонка на `UserProfile`:
```
challenge_tolerance String(10) default "balanced"  # gentle|balanced|direct-ish
   # ось «отражать/одобрять ↔ мягко вызывать»; авто-снижается, когда человек
   # отталкивает вызов. Отличается от preferred_style (тот про фразы/клише).
```

**Миграция `backend/alembic/versions/013_treatment_plan.py`** (паттерн как `009`/`012`):
`revision="013_treatment_plan"`, `down_revision="012_monetization"`.
`upgrade()`: `op.create_table("treatment_plans", ...)` + `op.add_column("user_profiles", challenge_tolerance, server_default="balanced")`.
`downgrade()`: drop_table + drop_column. Без бэкфилла. Запускается через
`alembic upgrade head` в `start.sh`.

## 2. Стойка хода (per-turn)

Новый метод `Orchestrator._assess_turn(message, history, active_focus_title="", session_id="")
-> tuple[dict, dict|None]` — **один** вызов `glm-4-flash`, возвращает темы +
стойку + сигналы. Вызывается в начале `process()`.

**Критично:** НЕ переиспользовать кэш `_classify_topics` (`_TTLCache`, 5 мин /
4 сообщения) — стойка должна быть свежей каждый ход. Решение: **убрать
топик-кэш и всегда делать один `_assess_turn` на ход** (задержка = один flash-
вызов/ход, было 0–1; flash быстрый, токены не критичны).

Таксономия `stance`:
```
quick_help  — просят технику/ответ → отвечать сразу, минимум расспросов
anamnesis   — данных мало / новая нить → 1-2 точечных вопроса, строим гипотезу
presence    — выговаривается/затоплен → просто быть рядом, без техник и структуры
socratic    — застрял в убеждении → открытый вопрос, мягко ставящий рамку под сомнение
challenge   — рационализирует/избегает и выдержит → уважительно назвать противоречие, НЕ одобрять
consolidate — естественная точка закрепления → отражение + 1 конкретная практика
crisis      — сигнал безопасности → кризисная ветка (keyword-детектор первичен)
```

Возвращаемый JSON (парсить защитно, как в текущем `_classify_topics`; при
сбое — безопасный дефолт `stance="presence"`):
```json
{"topics":["anxiety"], "stance":"socratic", "validate_level":1,
 "requesting_help":false, "venting":false, "terse":false, "crisis":false,
 "focus_alignment":"on|drift|redirect_request", "redirect_signal":false}
```
Промпт — новый файл `backend/app/agents/prompts/turn_assessment.txt`.

**Как стойка влияет на поток:**
- *Поведение синтеза:* новый `STANCE_INSTRUCTIONS: dict[str,str]` инжектится в
  user-сообщение синтеза вместо/над `PHASE_INSTRUCTIONS` (там же, где сейчас,
  `orchestrator.py:534`). `validate_level` → текстовая инструкция
  «эмоционального отражения: минимально/умеренно/много». Для `challenge`:
  «Не отражай и не одобряй автоматически. Мягко назови противоречие/избегание.
  Один прямой уважительный вопрос.» Для `presence`: «Никакой структуры, техник
  и заданий — просто будь рядом.»
- *Выбор агентов:* заменить текущий skip (`phase==INTAKE & exchange<=1 & len<40`)
  на stance-driven: `presence/quick_help` (терсно/выговаривается) и `crisis` →
  агентов не звать; `anamnesis` → пропустить агентов на первом зондировании;
  `socratic/challenge/consolidate` с темами → звать `_select_agents` как сейчас.
- *`SessionPhase` демотируется:* остаётся только для INTEGRATION/CLOSE-нюанса
  «близко к концу» (это честно временно́е) + farewell-маркеры. Блок
  `[ПРОГРЕСС СЕССИИ ...]` сохраняет инфо об остатке обменов.
- *Детерминированный fallback:* если `requesting_help=true` — всегда отвечать
  прямо независимо от стойки (страховка от мисфайра flash).

## 3. Повестка сессии (agenda)

На **WS-connect** (`messages.py`, рядом с загрузкой профиля) грузим
`TreatmentPlan`, чистой функцией `plan_service.compute_agenda(plan)` строим
строку = тайтл активного фокуса + rationale + «гибко следуй за человеком».
Без модельного вызова → нулевая задержка. Передаём в `orchestrator.process`
каждый ход; в синтезе её вес выше на первых 1–2 ходах сессии.

Путь авто-приветствия продолжения (`messages.py:207-272`, идёт мимо
оркестратора) — **дополнить**: вшить активный фокус в `continuation_prompt`,
чтобы приветствие открывалось к приоритету плана.

## 4. Жизненный цикл плана

Новый сервис `backend/app/services/plan_service.py`:
- `get_or_none(user_id, db)` — чтение.
- `build_initial_plan(user_id, history, long_term_memory, db)` — `glm-5`,
  первый раз после порога интейка (конец первой сессии / N обменов без плана):
  формулировка + 3–5 приоритизированных фокусов + `active_focus_id`=топ.
- `update_plan(user_id, history, long_term_memory, current_plan, db, redirect_signal=False)`
  — `glm-5`: пересборка формулировки, ре-приоритизация, продвижение/закрытие
  активного фокуса, запись `plan_summary`. SHA1 `plan_hash` dedup (skip-on-noop,
  как `memory_service`).
- `compute_agenda(plan)` — чистая.

Промпты `plan_build.txt`, `plan_update.txt` (glm-5, строгий JSON; при сбое
парсинга план не трогаем).

**Когда обновлять:**
- Основное — **в фоне после сессии**: хук на `session_limit_reached`/farewell в
  `messages.py` и в `sessions.py:continue_session` (там уже собраны `insights`).
- Сетка безопасности — лёгкий апдейт раз в N обменов, но только при
  `redirect_signal` или сильном прогрессе (чтобы не гонять glm-5 каждые 3 хода).

**Сигнал «не про это» (`redirect_signal`)** ловит per-turn стойка:
- *Немедленно (этот ход):* оркестратор при `redirect_signal` гасит ведение к
  фокусу в синтезе («следуй за человеком, не возвращай к фокусу») — без записи в БД.
- *Долгосрочно (фон):* `update_plan(..., redirect_signal=True)` де-приоритизирует
  отвергнутый фокус, поднимает следующий; при отталкивании вызова — снижает
  `challenge_tolerance`.

## 6. Промпты

**`orchestrator.txt` (правка):**
- Секцию «## Прогресс сессии» заменить на «## Как ты выбираешь способ ответа»
  (7 стоек простым языком, как инстинкт, не протокол).
- Добавить явное разрешение **не отражать/не одобрять и мягко вызывать**:
  отражение эмоций и одобрение полезны не всегда; иногда самое бережное —
  аккуратный вопрос, ставящий убеждение под сомнение или называющий избегание,
  без жёсткости, в рамках текущей иерархии приоритетов.
- «## Долгосрочный план работы (внутреннее, не озвучивать)»: Ника может получать
  рабочую гипотезу и текущий фокус; работает к нему **постепенно и незаметно**,
  никогда не объявляет «у нас план/протокол», не перечисляет фокусы, мгновенно
  отпускает тему по сигналу человека.

**Новые файлы:** `turn_assessment.txt` (flash), `plan_build.txt`, `plan_update.txt` (glm-5).

## 7. Риски

1. **Стойка vs топик-кэш** — стойка обязана быть свежей; не сливать в
   кэшируемый путь. Решение: убрать кэш, один `_assess_turn`/ход.
2. **Путь авто-приветствия идёт мимо оркестратора** — отдельно вшить agenda в
   `continuation_prompt`.
3. **Утечка плана в видимые ответы** (главный продуктовый риск): план в system
   помечен «не озвучивать»; промпт запрещает анонс протокола; `plan_summary` —
   отдельное мягкое поле для карточки, не сырая `formulation`. Опираемся на
   дисциплину промпта (жёсткий regex-фильтр рискован).
4. **Бэкомпат:** всё условно на непустом плане; миграция — только nullable/
   defaulted колонка.
5. **Задержка/стоимость glm-5:** весь план-пасс только в фоновых
   `asyncio.create_task` со своим `async_session()`; WS-ход не блокируется.
6. **Гонки фоновых задач:** `update_plan` читает свежую строку плана внутри
   своей сессии; в фон передаём dict/str, не detached-ORM (как уже сделано).
7. **Конкуренция фонов** (память/3, личность/ход, план): тяжёлый план — в
   основном post-session; mid-session — только при redirect/прогрессе.

## Верификация

1. **Миграция:** `cd backend && alembic upgrade head` создаёт `treatment_plans`
   и колонку; `alembic downgrade -1` откатывает. Проверить SQLite-схему.
2. **Бэкомпат (нет плана):** новый пользователь, первый диалог — поведение как
   сейчас (нет инжектов, `/plan-progress` → `has_plan=false`).
3. **Стойки:** прогнать сообщения, дающие разные стойки, и подтвердить по логам
   `turn_meta`/`agents_used`: «дай технику от тревоги» → quick_help, агенты по
   теме; «мне просто хреново, не хочу разбор» → presence, агентов нет; явное
   рационализирование → challenge/socratic без авто-одобрения.
4. **Анамнез→план:** провести первую сессию до конца → в фоне строится план
   (`build_initial_plan`); проверить строку `treatment_plans`, активный фокус,
   `plan_summary`. SessionEndCard показывает фокус + прогресс.
5. **Реприоритизация:** в чате «давай не про это сейчас» → этот ход не давит на
   тему (немедленно); после сессии `update_plan` понижает фокус, поднимает
   следующий; `challenge_tolerance` снижается при отталкивании вызова.
6. **Невидимость:** просмотреть ответы Ники — план/формулировка/слово
   «протокол»/перечни фокусов не всплывают в видимом тексте.
7. Запустить бэкенд (`uvicorn`) + фронт (`vite`), пройти полную сессию в
   браузере, проверить стрим и карточку конца сессии.
