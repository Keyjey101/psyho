# ТЗ: подготовка сервиса к запуску платного трафика

## Контекст и цель

Сервис работает, но пользователей нет. Начинаем закупать рекламу в тематических Telegram-каналах. Задача этого этапа — **не монетизация, а проверка гипотезы удержания**: возвращаются ли люди на второй день и какой источник трафика даёт возвращающихся.

Платёжная система (ЮKassa) сознательно НЕ подключается на этом этапе. Доступ выдаётся кредитами, монетизация эмулируется fake-door экраном.

**Главная метрика этапа: доля пользователей, вернувшихся на следующий день (D1 retention), в разрезе источника.**

Не метрики: количество стартов бота, число сообщений, «вовлечённость». Их логируем, но решения принимаем не по ним.

## Задача 1. Сквозная атрибуция трафика

### 1.1. Схема кампаний

Создать сущность `campaign` со справочником в БД:

| Поле | Описание |
|---|---|
| `code` | Короткий уникальный код, `[A-Za-z0-9_-]{1,32}`. Например `tg_bezfiltrov_01` |
| `utm_source` / `utm_medium` / `utm_campaign` / `utm_content` | Полные UTM-метки |
| `channel_name` | Человекочитаемое название площадки |
| `cost_rub` | Сколько заплачено за размещение (заполняется вручную в админке) |
| `placed_at` | Дата размещения |
| `is_active` | Флаг |

Кампании создаются через админку, а не хардкодом.

### 1.2. Вход через Telegram deep-link

Формат: `https://t.me/<bot>?start=<payload>`

**Критично:** payload в Telegram ограничен 64 символами и допускает только `A-Za-z0-9_-`. Поэтому в ссылку кладём **только `campaign.code`**, а полные UTM резолвим на бэке по справочнику. Не пытаться упаковать UTM в payload напрямую.

Обработка `/start`:
1. Распарсить payload, найти кампанию по `code`.
2. Если пользователь новый — записать атрибуцию в `user.attribution` (first-touch, перезаписи нет никогда).
3. Если пользователь существует — атрибуцию не трогать, залогировать событие `repeat_start` с новым кодом.
4. Payload не найден или пуст — источник `organic`.

Атрибуция **first-touch и неизменяемая**. Пользователь, пришедший из канала X и позже кликнувший ссылку из канала Y, навсегда остаётся за X.

### 1.3. Вход через веб

1. Лендинг принимает стандартные `utm_*` параметры.
2. Сохранять в `localStorage` (срок 30 дней) сразу при заходе, до любых действий.
3. При переходе в бота бэкенд генерирует/находит `campaign.code` по связке UTM и подставляет в ссылку `?start=<code>`.
4. Если пришли UTM без соответствующей кампании — создать её автоматически со статусом `auto_created`, чтобы трафик не терялся.

### 1.4. Генератор ссылок в админке

Страница, где по выбранной кампании отдаётся готовая ссылка на бота и ссылка на веб-версию с подставленными UTM, обе с кнопкой копирования. Без ручной сборки URL руками.

## Задача 2. Тесты как точка входа

Сейчас тесты лежат на главной и просто проходятся. Нужно превратить каждый тест в самостоятельную посадочную страницу — это основная точка входа для рекламы.

### 2.1. Отдельные URL

Каждый тест доступен по `/test/<slug>` и принимает UTM-метки. Примеры: `/test/anxiety`, `/test/burnout`, `/test/attachment`.

Каждая страница: заголовок с обещанием результата, время прохождения, кнопка старта. Без обязательной регистрации до начала.

### 2.2. Воронка теста

```
Открытие страницы → Старт теста → Завершение → Экран результата → Переход в бота
```

На каждом шаге — событие с сохранением `campaign_code`.

### 2.3. Экран результата

- Персональная интерпретация от LLM, а не просто балл.
- CTA в бота с сохранением атрибуции: `?start=<campaign_code>`.
- Кнопка «Поделиться результатом» — генерирует картинку-карточку **без персональных данных и без диагнозов**, только тема теста и приглашение пройти. Ссылка на карточке несёт `campaign.code = viral_<test_slug>`, чтобы виральный трафик отделялся от закупного.

### 2.4. Обязательное требование по безопасности

Если тест содержит пункты про суицидальные мысли или самоповреждение (например, вопрос 9 в PHQ-9), либо результат попадает в тяжёлую зону:

- Экран результата **обязан** показывать контакты живых кризисных служб выше и заметнее, чем CTA в бота.
- Такой результат **не сопровождается** предложением купить/потратить кредиты.
- Формулировки результата не содержат диагнозов. Только «результат опросника», «имеет смысл обсудить со специалистом».

Это не опциональная фича. Без неё трафик не запускается.

## Задача 3. Событийная модель

Одна таблица `events`, append-only:

```
id, user_id, event_type, campaign_code, payload_json, created_at
```

Обязательный набор `event_type`:

**Привлечение**
- `landing_view` — открытие лендинга/страницы теста
- `bot_start` — первый `/start`
- `repeat_start` — повторный `/start` с другим кодом

**Тесты**
- `test_started`, `test_completed`, `test_result_viewed`, `test_shared`

**Активация**
- `first_message` — первое сообщение пользователя в диалоге
- `message_3` — третье сообщение (порог осмысленного контакта)
- `session_completed` — завершённая сессия

**Удержание** (вычисляемое, а не логируемое)
- Возврат D1 / D3 / D7 — считать по `created_at` любого события пользователя относительно даты его `bot_start`

**Монетизация (fake door)**
- `credits_exhausted`
- `paywall_viewed` — показан экран тарифа с ценой
- `paywall_clicked` — нажата кнопка оплаты
- `email_submitted` — оставлен контакт в листе ожидания

**Безопасность**
- `crisis_detected` — сработал детектор кризисного состояния
- `crisis_resources_shown`

В `payload_json` **не класть тексты сообщений пользователя**. Только метаданные: длина, номер по счёту, тип. Тексты диалогов в аналитику не попадают ни при каких условиях.

## Задача 4. Кредиты и границы расходов

### 4.1. Механика

- Новый пользователь получает бесплатные сессии/кредитов (как сейчас).
- Кредиты/сессии не восстанавливаются автоматически. Исчерпание — триггер fake-door экрана.

### 4.2. Защита от неконтролируемых расходов

Обязательно, до первого рубля в рекламу:

- Лимит токенов на пользователя в сутки (жёсткий, независимо от кредитов).
- Глобальный дневной лимит расходов на LLM с автоматическим отключением приёма новых пользователей при достижении.
- Уведомление владельцу (админу) в Telegram при достижении 50% / 80% / 100% дневного лимита.
- Дашборд текущих расходов за сегодня и за месяц в админке.

### 4.3. Fake-door экран

При `credits_exhausted` показать реальный экран тарифа: цена, что входит, кнопка «Оплатить».

По нажатию — **не платёж**, а честный текст: оплата запускается в ближайшее время, оставьте контакт, дадим бесплатный период на старте. Форма сбора email/telegram.

Никакого обмана: не имитировать процесс оплаты и не запрашивать данные карты.

**Исключение:** если в сессии сработал `crisis_detected`, fake-door не показывается вообще. Человеку в остром состоянии нельзя упираться в стену «кредиты кончились». Для таких сессий — либо аварийный запас кредитов, либо прямая выдача кризисных контактов.

## Задача 5. Админ-страница аналитики

Вкладка в существующей админке. Стек — как в проекте (Vue).

### 5.1. Таблица источников

Строка на кампанию, колонки:

| Источник | Клики | Старты бота | Тест пройден | 1-е сообщение | 3-е сообщение | Вернулись D1 | Paywall клик | Затраты ₽ | CPA ₽ | Цена за D1-возврат ₽ |

- `CPA = затраты / старты бота`
- `Цена за D1-возврат = затраты / вернувшиеся D1` — **главная колонка таблицы**, по ней принимается решение о повторной закупке
- Конверсии между шагами показывать в процентах прямо в ячейке
- Сортировка по любой колонке, фильтр по периоду

### 5.2. Когортное удержание

Таблица: строки — недели привлечения, колонки — D1 / D3 / D7 / D14. С разбивкой по источнику.

### 5.3. Воронка

Наглядная воронка от клика до третьего сообщения, с выбором источника. Нужна, чтобы видеть, где именно отваливаются люди из конкретного канала.

### 5.4. Ввод затрат

Поле в карточке кампании для внесения суммы размещения. Без него не считается ни CPA, ни цена возврата.

### 5.5. Мониторинг безопасности

Отдельный блок: число `crisis_detected` за период, доля от сессий. Без содержимого диалогов — только счётчики. Это операционный индикатор: если доля высокая, креативы приводят слишком тяжёлую аудиторию и их надо менять.

## Задача 6. Приватность и соответствие

- Персональные данные не уходят в аналитику. `user_id` в событиях — внутренний, не telegram_id.
- Политика обработки персональных данных и согласие на обработку — до начала диалога (152-ФЗ).
- В интерфейсе и рекламных материалах не использовать слова «терапия», «лечение», «диагноз», «замена психологу». Сервис — поддержка и самоанализ.
- Явная плашка о том, что общение ведётся с ИИ, — при первом контакте.

## Критерии приёмки

Перед запуском трафика проверить вручную:

1. Переход по `t.me/bot?start=test_campaign` → в БД есть `bot_start` с этим кодом.
2. Тот же пользователь заходит по другой ссылке → атрибуция не изменилась, есть `repeat_start`.
3. Заход на `/test/anxiety?utm_source=x&utm_campaign=y` → переход в бота → атрибуция сохранилась через веб.
4. Прохождение теста целиком → все четыре события теста в БД.
5. Исчерпание кредитов → `paywall_viewed`, клик → `paywall_clicked`, форма работает.
6. В админке кампания видна, затраты вносятся, CPA и цена D1-возврата считаются верно.
7. Тестовое сообщение с кризисным содержанием → кризисные контакты показаны, fake-door не показан.
8. Превышение дневного лимита расходов → приём новых пользователей остановлен, уведомление пришло.
9. В таблице `events` нет ни одного текста сообщения пользователя.

## Порядок реализации

1. События и атрибуция (задачи 1, 3) — без этого остальное бессмысленно
2. Границы расходов и кризисный сценарий (4.2, 2.4) — без этого нельзя пускать трафик
3. Тесты как посадочные (задача 2)
4. Админка (задача 5)
5. Fake door (4.3)
6. Приватность и формулировки (задача 6)

Пункты 1 и 2 блокирующие. Остальное можно доводить параллельно с первыми размещениями.
